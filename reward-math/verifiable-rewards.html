7.1Rewards you can check

A reward model is a learned guess at what people prefer, and Module 8 shows what goes wrong when a policy pushes too hard on a guess. Some tasks do not need a guess. A math problem with a known final answer can be checked by comparing answers. Code can be checked by running tests. A verifier is a program that does such a check.

A verifiable reward uses the verifier's result as the reward. Training a policy this way is called RLVR, reinforcement learning with verifiable rewards, a name introduced in the Tülu 3 report (Lambert et al., 2024).

r(x, y) = \begin{cases} 1 & \text{if } y \text{ is correct, or the tests pass} \\ 0 & \text{otherwise} \end{cases}
(7.1)

Tülu 3 writes the verifier as v(x, y) and gives a correct answer a reward of α = 10 rather than 1 (its equation 8). The scale changes the size of updates but not which responses are favored.

7.2Same objective, different reward

RLVR keeps the objective from Module 5 and swaps the reward model for the verifier (Tülu 3, equation 7, in this site's notation):

\max_{{\theta}}\ \mathbb{E}_{y \sim {\pi_\theta}(\cdot \mid x)}\big[v(x, y)\big] - {\beta}\,\mathbb{D}_{\mathrm{KL}}\big[{\pi_\theta}(y \mid x)\,\big\|\,{\pi_{\mathrm{ref}}}(y \mid x)\big]
(7.2)

Tülu 3 optimized this with PPO.

7.3Checking an answer

Verifiers are simple but strict. For math, the response has to state its final answer in a form the checker can extract, which is then compared with the reference answer. For code, the program is run against tests. Tülu 3 also used instructions with checkable constraints, such as a required number of paragraphs, verified by code.

A binary reward is a sparse reward. A hard problem may give 0 for every attempt, and then there is nothing to learn from: every sample looks equally bad.

7.4Comparing within a group

A common way to get a baseline (Module 3) without training a value function is to sample several responses to the same prompt and compare them with each other. GRPO, group relative policy optimization, was introduced in the DeepSeekMath paper (Shao et al., 2024) and is covered in chapter 6 of the RLHF book. With one reward per response, its advantage is:

\hat{A}_i = \frac{r_i - \mathrm{mean}(r_1, \dots, r_G)}{\mathrm{std}(r_1, \dots, r_G)}
(7.3)

With binary rewards, correct answers get a positive advantage and wrong ones a negative advantage. When all samples are right, or all are wrong, the standard deviation is 0. Implementations add a small number to the denominator to avoid dividing by zero, every advantage is 0, and the prompt teaches nothing.

A code example works the same way. If the task is to write is_even(n) and the tests check 0, 3 and 10, a response that returns n % 2 == 0 passes all three and gets reward 1. A response that returns n < 5 passes the check for 0, fails 3 and 10, and gets 0.

7.6Exercises

  1. Can a verifiable reward be gamed?

    Yes. The reward checks only what the verifier checks. In the code example, a response that returned True for 0 and 10 and False otherwise would pass every test without solving the task. Weak tests and loose answer extraction are the openings.

  2. All eight samples for a prompt are wrong. What advantages does equation 7.3 give?

    All 0. The mean is 0 and the standard deviation is 0, so after the small number added to avoid division by zero every advantage is 0. The prompt contributes no learning signal.

  3. In a group of four, one answer is correct. What are the advantages?

    The mean is 0.25 and the standard deviation is √(0.25 × 0.75) ≈ 0.433. The correct answer gets (1 − 0.25)/0.433 ≈ 1.73, and each wrong answer gets −0.25/0.433 ≈ −0.58. A rare success is pushed up strongly.

  4. Tülu 3 gives a correct answer a reward of 10 instead of 1. Does that change GRPO's advantages?

    No. Multiplying every reward by 10 multiplies the mean and the standard deviation by 10 too, so each ratio in equation 7.3 is unchanged.
